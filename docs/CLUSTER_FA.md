# مدیریت واقعی چند سرور KANKI 0.4.0

حالت پیش‌فرض، نصب تک‌سرور قبلی است. حالت `KANKI_CLUSTER=1` پنل را به کنترل‌کنندهٔ مرکزی تبدیل می‌کند: هر نود لینوکس عامل مستقل، هستهٔ VPN و NAT دارد. کنترل‌کننده خودش در این حالت سرویس تونل محلی اجرا نمی‌کند. الگوریتم‌های AES-GCM، FEC، Repeat، Jitter و wire protocol با 0.3.0 یکسان‌اند.

## نصب کنترل‌کنندهٔ تازه

روی Debian/Ubuntu تازه با systemd:

```bash
curl -fsSL https://raw.githubusercontent.com/kankiturk8770/Testkanki/main/install.sh | sudo KANKI_CLUSTER=1 bash -s -- panel.example.com
```

نصب‌کننده گواهی TLS معتبر را با Caddy خودکار می‌گیرد؛ API پورت 8765 فقط محلی می‌ماند. توکن مدیریت از `/etc/kanki-admin.env` خوانده می‌شود. زمان همهٔ ماشین‌ها با NTP همگام باشد. API عامل فقط HTTPS قبول می‌کند و redirect را رد می‌کند؛ CA خصوصی از `KANKI_CONTROLLER_CA` قابل تعیین است.

در بخش سرورها، نود را با دامنه/IP عمومی، پورت و تنظیمات انتقال بسازید. توکن نود فقط یک بار نمایش داده می‌شود؛ آن را در فایل خصوصی `token.txt` با مجوز 0600 روی ماشین مقصد قرار دهید. هر نود اعتبار جدا دارد و به API مدیریت دسترسی ندارد.

روی نود **تازه و اختصاصی**:

```bash
sudo bash deploy/install-node.sh https://panel.example.com < token.txt
sudo systemctl status kanki-agent kanki-vpnd kanki-gateway
sudo journalctl -u kanki-agent -u kanki-vpnd --since '10 minutes ago'
```

اگر نصب به‌دلیل TLS یا قطع شبکه نیمه‌کاره ماند، پس از رفع مشکل `sudo bash deploy/install-node.sh https://panel.example.com --resume` را اجرا کنید؛ هویت و journal حفظ می‌شوند.

نصب‌کننده ابتدا تنظیمات امضاشده را دریافت و با executable واقعی اعتبارسنجی می‌کند، سپس سرویس‌ها را راه می‌اندازد. ترافیک دیتای کاربران مستقیماً به UDP نود می‌رود؛ کنترل‌کننده در مسیر بسته‌ها نیست. پورت UDP انتخاب‌شده را در فایروال باز کنید. تغییر listener، MTU یا پورت در حین کار API ندارد؛ برای تغییر آن نود جدید بسازید و دستگاه‌ها را منتقل کنید. از بازنصب با حذف state برای دورزدن خطای هویت استفاده نکنید.

در پنل کاربر بسازید، «دستگاه‌ها» را باز کنید و هر slot را به یک نود تخصیص دهید. اشتراک فقط پروفایل‌هایی را برمی‌گرداند که هستهٔ نود نسخهٔ لازم را واقعاً بارگذاری و عامل آن را تأیید کرده است. تا آن زمان پاسخ اشتراک 503 است. همان لینک HTTPS در اپ اندروید مصرف می‌شود؛ فرمت نسخهٔ 1 حفظ شده است.

## قطع ارتباط، انتقال و محدودیت اتصال

عامل هر سه ثانیه تنظیمات را pull می‌کند. هر مجوز حداکثر 30 ثانیه معتبر است. در قطع کنترل‌کننده، هسته پس از پایان مجوز ترافیک را رد می‌کند. برای توقف کاربر/نود یا rotation کلید، در شرایط قطع ارتباط و با اختلاف ساعت مجاز، حدود 45 ثانیه مهلت در نظر بگیرید؛ پاسخ API مهلت را اعلام می‌کند. ساعت با اختلاف بیش از 10 ثانیه از کنترل‌کننده رد می‌شود.

یک دستگاه هم‌زمان فقط به یک نود منتسب است. جابه‌جایی، پایان آخرین مجوز صادرشدهٔ نود قبلی + 12 ثانیه حاشیهٔ اختلاف ساعت را صبر می‌کند. این انتظار ممکن است تا حدود 45 ثانیه باشد؛ پنل زمان مجاز انتقال را نشان می‌دهد. تعداد slotها بین نودها مشترک است؛ به معنی مجازبودن همان کلید روی همهٔ سرورها نیست. اتصال دو گوشی با همان slot می‌تواند باعث رد endpoint دوم شود؛ هر گوشی پروفایل خودش را استفاده کند.

## حجم مشترک و ذخیرهٔ پایدار

کنترل‌کننده اعتبار حجمی را با transaction دیتابیس بین نودها تقسیم می‌کند. مجموع اعتبار صادرشده هرگز از سقف کاربر فراتر نمی‌رود. صفر در پنل نامحدود است، ولی عامل حتی برای کاربر نامحدود به هسته اعتبار محدود و افزایشی می‌دهد تا صفر در فایل نود به معنی مجوز آزاد نباشد.

هسته پیش از عبور IP، رزرو حجم را در journal با `fsync` ثبت می‌کند؛ بلوک رزرو حداکثر 64 KiB است. حجم wire تکرارها/FEC دوباره از کاربر کسر نمی‌شود. در crash، باقیماندهٔ بلوک رزروشدهٔ هر حساب روی همان نود سوخته محسوب می‌شود؛ در نتیجه ممکن است تا 64 KiB برای هر حساب/نود از حجم قابل استفاده کم شود، ولی حجم مصرف‌شده دوباره آزاد نمی‌شود. journal به‌صورت اتمیک compact می‌شود تا رشد آن به ازای هر بسته ادامه نداشته باشد. هزینهٔ fsync روی دیسک کند باید هنگام تست ظرفیت سنجیده شود.

«ترافیک» مجموع بایت IP مشاهده‌شده است؛ «ثبت پایدار» رزرو محافظه‌کارانه و «رزرو» اعتبار صادرشدهٔ مرکزی است. این سه الزاماً برابر نیستند. شمارندهٔ نمایشی ترافیک ممکن است در crash یا حذف و برگشت حساب از یک نود، کمتر از مصرف محافظه‌کارانه باشد؛ سقف اجرایی از journal می‌آید.

اعتبار استفاده‌نشدهٔ نود آفلاین خودکار پس گرفته نمی‌شود؛ پس از انتقال دستگاه ممکن است بخشی از سهمیه روی نود قبلی باقی بماند. این محدودیت برای جلوگیری از دوباره خرج‌شدن حجم است. کم‌کردن سقف زیر مجموع اعتبار صادرشده رد می‌شود؛ تمدید با افزایش سقف انجام می‌شود. برای آزادشدن اعتبار، state یا journal را حذف نکنید.

## مهاجرت نصب تک‌سرور موجود

ابتدا از DB، config و status پشتیبان بگیرید. موتور و پنل را متوقف کنید تا snapshot نهایی ایجاد شده باشد. اسکریپت حساب‌هایی را که آمار نهایی ندارند رد می‌کند. روی سورس جدید:

```bash
sudo systemctl stop kanki-admin kanki-gateway kanki-vpnd
sudo python3 agent/migrate_local.py --offline \
  --db /var/lib/kanki/admin.sqlite3 --status /var/lib/kanki/status.txt \
  --config /etc/kanki/kanki.conf
```

ابزار backup جداگانه می‌سازد، مصرف قبلی را به `base_usage` وارد و config محلی را منقضی می‌کند. DB و config در فایل‌های جدا هستند؛ این مرحله حتماً آفلاین انجام شود. ابزار مالک فایل‌های DB و config را حفظ می‌کند تا پنل (کاربر `kanki`) بعد از مهاجرت دسترسی داشته باشد. سپس `KANKI_CLUSTER=1` را در `/etc/kanki-admin.env` تنظیم و نصب‌کنندهٔ کنترل‌کننده را با همین متغیر اجرا کنید. دستگاه‌ها را به نودهای تازه تخصیص دهید. تبدیل همان میزبان قبلی به نود نیازمند جداسازی مسیرهای state و واحدهای systemd است و در نصب‌کنندهٔ ساده پشتیبانی نشده؛ آن را نود تازه فرض نکنید.

برای بازیابی خرابی، `agent.json`، `credit.log` و credential نود را یک مجموعه بدانید. بازگرداندن journal قدیمی اعتبار مصرف‌شده را برمی‌گرداند و پشتیبانی نمی‌شود. در گم‌شدن هویت، نود قبلی را غیرفعال و نود جدید بسازید؛ اعتبار قبلی خودکار آزاد نمی‌شود. SQLite مرکزی و journalها باید روی دیسک پایدار با semantics درست fsync باشند. HA چند کنترل‌کنندهٔ مستقل و ادغام DBها پیاده نشده‌اند.

## تکرار آزمون‌ها

```bash
bash tests/run.sh
python3 tests/test_panel_cluster.py
sudo python3 tests/cluster_netns.py
```

تست آخر دو نود و دو کلاینت واقعی TUN را در namespace جدا با کنترل HTTPS و CA آزمایشی اجرا می‌کند؛ سقف مشترک و restart موتور را می‌سنجد. root، TUN، openssl، NET_ADMIN و SYS_ADMIN لازم است. برای smoke نصب روی VPS، boot/reboot و تنظیم فایروال همچنان میزبان واقعی لازم است.
